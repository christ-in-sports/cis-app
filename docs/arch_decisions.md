# CIS Architecture Decisions

> An ADR-style (Architecture Decision Record) log of technical and architecture decisions.
> This is a living doc. `project_spec.md` Part 2 is updated whenever a technical decision
> changes, but it records only the *current state* — it has no room for the reasoning or the
> alternatives that were considered. This file preserves that reasoning. Keep it current.
>
> **This file is for technical/architecture decisions only.** Product and scope decisions that
> deviate from `prd.docx` go in [`decisions.md`](./decisions.md). The current tech stack lives
> in [`project_spec.md`](../project_spec.md) §2.1 — that is current state, not a decision-log
> entry.

## When to add an entry

Add an entry whenever a technical decision is made or changed that a future contributor would
otherwise have to guess the reasoning for — a new library or pattern, a schema or RLS approach,
an integration design, or a reversal of an earlier choice. Update `project_spec.md` in the same
PR, and link to it from the entry's Reference.

Entries are never deleted. If a decision is reversed, mark the old entry **Superseded** and link
to the entry that replaces it.

## Entry format

Newest entries go first (reverse-chronological). Each entry is a `### YYYY-MM-DD — Title`
heading followed by:

- **Status:** `Proposed`, `Accepted`, or `Superseded` (if Superseded, link to the entry that
  supersedes it)
- **Context:** the problem or question that prompted this
- **Decision:** what was decided
- **Consequences / tradeoffs:** what this makes easier or harder, and what was given up
- **Reference:** the `project_spec.md` section it updates, if any, and/or the Linear issue

## Decisions

### 2026-10-22 — Kid photos in a private bucket, written with the user's own session and read through signed URLs
- **Status:** Accepted
- **Context:** Photos are required again (`decisions.md`, 2026-10-22). The 2026-09-21 design depended on copying photos from Google Drive and named objects by kid ID. Neither works now: photos come from parents through the app, and a new kid has no ID until `register_kid()` creates them, yet the photo is required for that same registration.
- **Decision:**
  - **Storage:** a private `kid-photos` bucket (WebP/JPEG, about 2 MB max). Objects get random names (`<uuid>.webp`). `kids.photo_path` (unique) holds the path and `kids.photo_updated_at` records when it was set. The browser resizes and crops to about 512 px square WebP before uploading, which also strips EXIF/GPS.
  - **HEIC input, never HEIC storage:** many parents pick iPhone photos, which are HEIC. The form accepts `.heic`/`.heif`, decodes them with the browser's own decoder where it can (Safari), and otherwise lazy-loads the `heic-to` converter (libheif compiled to WASM, pinned at 1.6.6, its `/csp` build so no `unsafe-eval` is needed) only for that file. `heic-to` is LGPL-3.0, as libheif is; it is used unmodified as an npm dependency. The alternative, `heic2any`, is MIT-licensed but has not been updated since 2023 and bundles the same libheif. The result goes through the same WebP resize, so the bucket never holds HEIC, which Chrome, Firefox and Android can't display. The conversion happens in the browser because `sharp`'s prebuilt binaries on Vercel don't decode HEIC.
  - **Upload, then attach:** the browser uploads first. `register_kid()` (new or returning kid) or `set_kid_photo(kid, path)` (replacing a photo) then checks the object exists, was uploaded by the caller (`owner = auth.uid()`), and isn't another kid's photo, and sets the path in the same transaction. `register_kid()` rejects a new kid, or a returning kid without a photo, when no path is given. That requirement shipped with the parent form (ENG-24), not with the schema (ENG-22), so `main` stayed deployable: both functions share an internal `attach_kid_photo()` that does the validation. `register_kid()` gained a fifth argument and a third result column (the replaced path, which the Server Action deletes after the registration is saved), so the four-argument function was dropped rather than left beside it, otherwise a kid could still be registered without a photo by calling it with fewer arguments. A kid on a team cannot be re-registered, so for them `replaceKidPhoto` is the only way to add or change a photo; the parent form offers it on the "on a team" screen. `set_kid_photo()` allows Admin or the kid's `parent_user_id` and returns the old path.
  - **No service role:** every step uses the signed-in user's Supabase client, so storage policies and the functions' own `has_role()` checks are the permission boundary, not the Server Action. With the service role, `auth.uid()` inside the functions would be null and the TypeScript would become the real boundary. Storage policies: INSERT allows `has_role('admin')` or `has_role('parent')`. SELECT allows Admin, or finds the kid through `kids.photo_path = name` and requires `can_read_kid(kid.id)`, or the uploader while no kid references the object (for the form preview). "Referenced by any kid" comes from a small `SECURITY DEFINER` function, `kid_photo_attached()`, because a plain subquery on `kids` is filtered by the caller's RLS: a parent whose kid was reassigned would otherwise look like the uploader of an unreferenced object. DELETE allows Admin or the uploader, and only once no kid references the object, so a referenced photo can't be removed even through the Storage API. There is no UPDATE policy.
  - **Replace:** the Server Action deletes the old object through the Storage API after the new path is saved. Postgres can't, because `storage.protect_delete()` blocks direct deletes. Objects no kid references (abandoned uploads, and old photos the replacer wasn't allowed to delete) are deleted by hand when needed, not by a scheduled job: the director chose not to run Vercel Cron for a few leftover files of about 40 KB. List them in the Supabase SQL editor with `select o.name, o.created_at from storage.objects o where o.bucket_id = 'kid-photos' and not exists (select 1 from public.kids k where k.photo_path = o.name) order by o.created_at;` and delete them from Dashboard > Storage > kid-photos or the Storage API, because a SQL `delete` is refused by `storage.protect_delete()`. Leave anything uploaded in the last day, which may belong to a form someone is still filling in.
  - **Read:** roster pages sign the visible paths in one `createSignedUrls(paths, 3600)` call with the user's client. `KidAvatar` keeps the first URL it received for a `photo_path` across the attendance 10-second `router.refresh()`, and switches only when the path changes or the image fails to load (expired URL). It uses a plain `<img>`, not `next/image`, so photos don't go through Vercel's image optimizer.
- **Alternatives considered:** a public bucket (links never expire and can't be revoked; ruled out for minors); proxying every photo through a Next.js route (works, but every image costs a Vercel function call and bandwidth); naming objects `<kid_id>/…` (impossible before a new kid exists); Supabase image transformations (paid plan, and unnecessary when we store small images); TanStack Query for URL caching (not installed, too much for one component); storing HEIC as uploaded (most viewers' browsers can't display it); converting HEIC on the server (no HEIC decoder in `sharp` on Vercel).
- **Consequences / tradeoffs:** A photo is visible to exactly the readers of the kid's row, and once it is replaced only its uploader and Admin can still read the old file (until cleanup), because the SELECT policy for everyone else needs a referencing kid. Coach access follows `coaches_kid()`, which checks the team link and not the Coach role, so a coach whose role was revoked but who is still linked to a team keeps seeing that team's photos, exactly as they keep seeing the rest of the roster row; that gap is not widened here. Archived attendance shows no photos, because `attendance_day_roster()` deliberately doesn't widen kid access. A signed URL works for anyone holding it until it expires (one hour). Each roster refresh still makes one bulk signing request. Unattached uploads stay in the bucket until someone deletes them, and no service role is used for photos anywhere. CSV-imported kids have no photo until a parent or Admin adds one. A HEIC upload in a non-Safari browser downloads the converter (about 0.8 MB gzipped) the first time; a HEIC file converts in about a second.
- **Reference:** `project_spec.md` §1.5, §2.2, §2.4; supersedes [2026-09-23 — Drop kid photos entirely](#2026-09-23--drop-kid-photos-entirely); Linear [ENG-21](https://linear.app/cis-app/issue/ENG-21), [ENG-22](https://linear.app/cis-app/issue/ENG-22), [ENG-23](https://linear.app/cis-app/issue/ENG-23), [ENG-24](https://linear.app/cis-app/issue/ENG-24)

### 2026-10-21 — Resend for transactional email; sending never blocks a save
- **Status:** Accepted
- **Context:** The servant registration confirmation (ENG-19) is the app's first outbound email. Supabase Auth's built-in mailer only sends auth messages, and it is rate-limited, so it cannot send this one.
- **Decision:** Resend, through its `resend` SDK, called only from server code (`src/lib/email/send-servant-confirmation.ts`, marked `server-only`). It reads `RESEND_API_KEY` and `EMAIL_FROM`. With no key it does nothing, which is how local dev and e2e tests run without sending anything. The message text is built by a separate pure function so it can be tested, and it leaves out DOB, home address and emergency contacts. The Server Action sends only when `submit_servant_registration()` reports the row is new, and a failure is caught, logged by error name only, and shown to the servant as a soft notice: the registration is already saved.
- **Consequences / tradeoffs:** A person who edits their registration later gets no second email, by design. A delivery failure is not retried. A human must add both env vars in Vercel and verify the sending domain in Resend before the first real send. Later emails (for example parent receipts) can reuse the same module pattern.
- **Reference:** `project_spec.md` §2.2; Linear [ENG-19](https://linear.app/cis-app/issue/ENG-19)

### 2026-10-21 — Roleless users are redirected to the servant form by layouts, not by middleware
- **Status:** Accepted
- **Context:** A new servant has no role until an Admin assigns one, and the only thing they can use is the registration form. Middleware only has the Supabase session and would need an extra database query on every request to know whether a user holds a role.
- **Decision:** `redirectIfRoleless()` (`src/lib/auth/servant-gate.ts`) runs in the home page and in the Sports, Attendance and Registration layouts, where the roles are already being read. The form route itself is open to any signed-in user.
- **Consequences / tradeoffs:** This is UX only: RLS already returns nothing to a roleless user. A new role-gated area has to call the helper in its layout. In the Registration layout it runs inside the streamed nav, so the redirect happens after the first paint. There is no Spiritual layout yet, so that area is not covered until it exists.
- **Reference:** Linear [ENG-19](https://linear.app/cis-app/issue/ENG-19)

### 2026-10-21 — Servant registration: its own table, written only through a SECURITY DEFINER function
- **Status:** Accepted
- **Context:** Servants register each season (see `decisions.md`, 2026-10-21). The record holds DOB, home address and emergency contacts, and the person filling it in usually has no role yet, so no role-based policy can describe them.
- **Decision:** A new `servant_registrations` table, one row per (`user_id`, `season_id`), instead of reusing the kid `registrations` table: the two share almost no fields and have different readers. RLS allows `SELECT` for `user_id = auth.uid()` or `has_role('admin')`; there are no write policies and `INSERT`/`UPDATE`/`DELETE` are not granted to API roles. Writes go through `submit_servant_registration(jsonb)`, which any signed-in user may call (a servant has no role). It takes `user_id` from `auth.uid()`, `season_id` from the current season and `email` from `auth.users`, upserts on (`user_id`, `season_id`), and returns whether the row was new so the app sends the confirmation email once. The shape rules (sessions, sub-teams, "Other") are CHECK constraints, mirrored by the Zod schema `servantRegistrationSchema`. A new policy lets any signed-in user read the current season, replacing the Parent-only one.
- **Consequences / tradeoffs:** A caller cannot move a row to another user or season, which a table policy could not prevent. Not serving discards the session answers instead of keeping an earlier "yes". Every signed-in user can now read the current season's name and dates, which are not sensitive; past seasons stay hidden from non-staff. The same pattern as `register_kid()`. Hosted needs the migration applied by hand.
- **Reference:** `project_spec.md` §1.5, §2.4; Linear [ENG-18](https://linear.app/cis-app/issue/ENG-18)

### 2026-10-20 — `profiles` is readable only by its owner and Admin; users may edit only their display name
- **Status:** Accepted
- **Context:** The baseline schema (inherited from the tournament prototype) had `"Profiles viewable by everyone"` (`FOR SELECT TO public USING (true)`) and `SELECT` granted to `anon`. The anon key is public, so anyone, signed in or not, could list every account's email and display name from `/rest/v1/profiles`. With servants and parents signing up, that is a ready-made phishing list for a church's families. Separately, `"Users can update own profile"` had no column restriction, so a user could rewrite their own `email`, which the Admin roles screen shows when an Admin decides who gets a role.
- **Decision:** One `SELECT` policy for `authenticated`: your own row, or all rows if you hold `admin`. `anon` has no privileges on the table. Updates are limited to the caller's own row and, by a column-level grant, to `display_name` only; `email` mirrors `auth.users.email` and is maintained by the SECURITY DEFINER auth triggers. Insert, delete and truncate are not granted through the API (profiles are created by the signup trigger and removed by the `auth.users` cascade, neither of which this affects).
- **Consequences / tradeoffs:** A non-Admin can no longer see anyone else's name. Today nothing needs that: the only readers are the Admin roles screen and the team coach picker. If a screen later needs another person's name (for example, who recorded a score), give it a narrow view or policy rather than reopening the table. A user can still set their own display name to anything, so the roles screen shows the email beneath the name. Hosted needs this migration applied; the app code does not depend on it, so deploy order does not matter.
- **Reference:** `project_spec.md` §2.5; Linear [ENG-16](https://linear.app/cis-app/issue/ENG-16)

### 2026-10-19 — Role assignment: Admin-only screen, one Server Action per change, guards in the database
- **Status:** Accepted
- **Context:** With signup creating roleless accounts (see the entry below), an Admin needs a way to grant roles without SQL. Two rules cannot be expressed by the `"admin manage roles"` table policy: an Admin must not be able to remove their own admin role (nobody could open the screen again), and `granted_by` must be trustworthy.
- **Decision:** `/admin/roles` lists every account with one tick box per `app_role`, people with no role first. Each tick is a Server Action (`grantRole` / `revokeRole` in `src/app/(registration)/admin/roles/actions.ts`) that authenticates the caller as Admin, validates with a Zod schema, and writes `user_roles` through the existing RLS policy. Two triggers on `user_roles` enforce the rest: one rejects deleting your own `admin` row (`23001`), and one stamps `granted_by` from `auth.uid()` so a request cannot forge it. System deletes (the profile cascade, the service role, migrations) have no `auth.uid()` and are unaffected. The tick box for your own Admin role is disabled in the UI as an explanation only.
- **Consequences / tradeoffs:** Only Admin can assign roles; Program Team cannot (`project_spec.md` §1.5 gives no other role that power). Removing the last Admin is still possible by another Admin removing them; a "last Admin" guard was left out as unnecessary while the self-removal rule holds. Saves are immediate with no confirm step, since every change is reversible from the same screen. Page order is fixed at load so rows do not move while ticking.
- **Reference:** `project_spec.md` §1.4; Linear [ENG-16](https://linear.app/cis-app/issue/ENG-16)

### 2026-10-19 — Roles are checked only through `has_role()`; signup creates roleless accounts
- **Status:** Accepted. Supersedes the `is_staff()` / `is_coach()` part of [2026-09-22 — Roles modeled as a `user_roles` join table](#2026-09-22--roles-modeled-as-a-user_roles-join-table-not-a-role-array-on-user)
- **Context:** The attendance and season policies still called `is_staff()` (meaning admin) and `is_coach()` (admin or coach), and several pages read the `profiles.is_staff` / `is_coach` flags directly. The names hid which role was meant. Signup only set those flags and never wrote `user_roles`, so every account created after the roles migration had flags but no roles. The `"Users can update own profile"` policy has no column restriction, so any signed-in user could set the flags on themselves, which showed them staff controls in the UI (RLS still blocked the writes).
- **Decision:** Every policy, SECURITY DEFINER function and server check names the role it means: `has_role('admin')`, or `has_role('admin') or has_role('coach')` where an Admin may also act as a Coach. `is_staff()`, `is_coach()` and the `profiles.is_staff` / `is_coach` columns are dropped, after a backfill of `user_roles` from the flags. Signup (`SERVANT_SIGNUP_CODE`, one shared code) creates a profile and nothing else; `handle_new_user()` ignores any `signup_role`. Roles are granted only by an Admin. Server pages read roles with `getMyRoles()` / `checkRole()` from `src/lib/auth/roles.ts`.
- **Consequences / tradeoffs:** Permissions can be read against the Role Permission Matrix line by line, and dropping the columns closes the self-escalation hole. The cost is a role query per page that needs several answers (`getMyRoles()` does it in one). Until the Admin role screen ships, new servants have no access, which is intended. The `"Users can update own profile"` policy let a user change their own email; that, and the public read policy on `profiles`, are fixed in [2026-10-20 — `profiles` is readable only by its owner and Admin](#2026-10-20--profiles-is-readable-only-by-its-owner-and-admin-users-may-edit-only-their-display-name). Program Team still cannot read attendance, past seasons or the full roster screen, exactly as before; the matrix does not list attendance for Program, so this is flagged, not changed.
- **Reference:** `project_spec.md` §1.4, §2.5; Linear [ENG-16](https://linear.app/cis-app/issue/ENG-16)

### 2026-10-08 — Sports writes: thin Server Actions over a service layer, courts shared across blocks, trigger functions off the API
- **Status:** Accepted
- **Context:** The competition database functions (ENG-12) do the atomic work, but several decisions sit between a click and a call: which teams a division has, seeding a knockout from a finished league, the per-sport rules for a result, and where a game goes on a game day. The prototype made all of these in browser code, in several separate writes.
- **Decision:** (1) `src/app/sports/actions.ts` is thin, like the registration actions: it authenticates, checks Admin or Program Team (`checkAnyRole`, a list-taking generalisation of `checkRole`), validates with the Zod schemas in `src/lib/validation/competition.ts`, then calls an operation in `src/lib/competition/service.ts`, which takes a Supabase client. Everything that must be atomic is one database function call from there, never several writes. (2) The Admin / Program Team check in the action is UX only; RLS and the `has_role()` checks inside the functions remain the boundary, and the end-to-end tests drive the actions through PostgREST as real signed-in users to prove it. (3) There is no game-day table: a game carries its own date, time and court, and the scheduler is given the cells already held on that date by **every** block, because courts are shared between Juniors and Ambassadors and between sports. A game whose time does not fall on the day's slot grid cannot be mapped onto it and is ignored. (4) Clearing a game day takes only unplayed games off it; a played game keeps its date, time and court, since that is where and when it was played. (5) The three trigger functions the security advisor flagged as callable through the API (`guard_sport_block_shape`, `set_team_season`, `set_day_season`) have EXECUTE revoked; triggers do not need it.
- **Consequences / tradeoffs:** The same operations run in the app and in the tests, so what is tested is what ships. Sharing courts means scheduling one block can fail to place games that a lone block would have fitted, which is the point. Two blocks with different game lengths on the same date can still overlap in time without sharing a grid cell, because only slot-aligned games are considered; scheduling such blocks on separate days avoids it. League standings use head-to-head before goal difference by default (`head_to_head_first`); the library supports the prototype's order too, but nothing in the app lets an admin choose yet, pending the Director's answer.
- **Reference:** Linear [ENG-14](https://linear.app/cis-app/issue/ENG-14), parent [ENG-10](https://linear.app/cis-app/issue/ENG-10)

### 2026-10-08 — Sports competition: sport blocks, an explicit progression graph, computed standings, writes only through functions
- **Status:** Accepted
- **Context:** The prototype it replaces (see 2026-10-07) stored standings, guessed a knockout game's next game from its round and bracket name, and wrote from the browser in several separate calls. That sent the 5th-place winner into the Final, never filled the 5th–8th bracket for some formats, and let results, standings and matches fall out of step.
- **Decision:** (1) A `sport_blocks` row is one sport for one division in one season, with a format (`league`, `knockout`, `league_knockout`) and, for leagues, a structure (`round_robin` or `groups`). Teams are the season's `ministry_teams`, with no sport of their own. (2) Each `games` row names where its winner and loser go (`winner_to_game_id` + slot, or `winner_place`), so the bracket is a graph the database can validate and no code has to infer it. (3) Standings are **not stored**; they are computed from `game_results` in TypeScript (`src/lib/competition/standings.ts`). Only each team's final place in a finished block is stored, in `sport_block_places`. (4) `games`, `game_results` and `sport_block_places` have no write policy; every write goes through a `SECURITY DEFINER` function (`create_sport_block_games`, `record_game_result`, `clear_game_result`, `complete_sport_block`, `set_game_schedule`, `reset_sport_block`) that locks the block, validates, advances teams and stamps `recorded_by` and `recorded_at` from `auth.uid()` and `now()`. `sport_blocks` is written directly by Admin and Program Team, but its `status` column is not writable by anyone; only the functions move it. (5) `games.event_id` is a nullable uuid with no foreign key until the calendar's `Event` table exists.
- **Consequences / tradeoffs:** A result, the teams it advances and its stamps change together or not at all, and standings cannot disagree with scores. Re-ranking costs a read of a block's games and results, which is a few dozen rows for 6–8 teams. The ranking rules are in TypeScript, so `complete_sport_block` for a league trusts the caller's ranked list and only checks it is a permutation of the block's teams. Editing a result is blocked once a later game it fed has been played with a different team; a score correction that keeps the same winner is always allowed. Format, sport, division and season are frozen once games exist and change only through `reset_sport_block`.
- **Reference:** `project_spec.md` §2.4; Linear [ENG-12](https://linear.app/cis-app/issue/ENG-12), parent [ENG-10](https://linear.app/cis-app/issue/ENG-10)

### 2026-10-08 — `ministry_teams.session` renamed `division`; team writes stay Admin-only, reads open to every role
- **Status:** Accepted
- **Context:** `registrations` already spells Juniors/Ambassadors `division` (`project_spec.md` §2.4), but `ministry_teams` still said `session` and allowed null ("both"). A standings table needs every role to read team names, while the permission matrix (§1.5) gives Program Team no roster or team update.
- **Decision:** Rename the column to `division`, make it `NOT NULL` with a named CHECK, add `season_id` (defaulted to the current season by a trigger, the same pattern as `set_day_season()`) and an optional `color`, and make `(season_id, division, name)` unique. Reads are open to any user with any app role (`has_any_role()`); writes stay Admin-only. Any role may also read the current season. `attendance_groups.session` is left as it is. A database trigger tying a registration's team to the registration's division was considered and not added, because the bulk "assign to team" action on the teams screen does not filter by division today.
- **Consequences / tradeoffs:** One naming for one concept on teams. A division mismatch between a kid and their team is not blocked by the database, so it must be handled where kids are assigned to teams. The team screen now requires a division when creating a team.
- **Reference:** `project_spec.md` §2.4; Linear [ENG-12](https://linear.app/cis-app/issue/ENG-12)

### 2026-10-07 — Prototype tournament schema removed, not migrated
- **Status:** Accepted
- **Context:** A "Tournament" module was built before the PRD and spec existed. It ran on its own permission model (`tournament_members`, share codes) and its own `teams`, separate from `ministry_teams`, with no season or division. Its RLS let any signed-in user insert themselves into a tournament as `owner`, and let any member promote themselves to `admin`. All of its data is test data.
- **Decision:** Drop all eleven tournament tables and `get_my_tournament_ids()` in one migration (`20261007230000_drop_tournament_prototype.sql`), delete the routes and components that used them, and remove the `firebase` dependency (only the dropped push tables needed it). The replacement is a season-scoped competition feature (sport blocks, games, results) that uses `has_role()` like the rest of the app.
- **Consequences / tradeoffs:** The security holes close immediately and no second permission model remains. The prototype's useful logic (fixtures, tiebreaks, scheduler) is ported from git history (`b4a77a6`) rather than kept in place. There is no sports competition feature until the replacement ships (ENG-12 to ENG-15); nothing real is lost. Push notifications are redesigned in v1.0.
- **Reference:** Linear [ENG-11](https://linear.app/cis-app/issue/ENG-11), parent [ENG-10](https://linear.app/cis-app/issue/ENG-10)

### 2026-10-05 — Payments are their own table, keyed on registration, written only through functions
- **Status:** Accepted
- **Context:** ENG-9 has an Admin record payments by hand (amount and method, partial payments allowed) before Stripe exists. The spec's `Payment` entity was keyed on `kid_id`, with an open question about moving it to `registration_id`. The simplest option would be `paid_at` / `paid_by` columns on `registrations`, mirroring consent.
- **Decision:** A `payments` table with one row per payment received: `registration_id`, `amount_cents` (integer, CHECKed between 1 cent and $1,000), `method` (CHECKed to `cash` / `venmo` / `paypal`), `received_at` and `recorded_by`. Writes go only through `record_payments(ids[], amount_cents, method)` and `delete_payment(id)`, both `SECURITY DEFINER` and admin-only. The table has **no** write policy. RLS lets Admin and the kid's linked parent read it, and nobody else. Program Team and coaches are deliberately excluded, unlike the rest of the kid's record. The fee and the method details are code constants (`src/lib/registration/payment.ts`), like the waiver link.
- **Consequences / tradeoffs:** Partial payments need more than one row per registration, so columns on `registrations` were ruled out. Keying on the registration scopes a payment to its season, which answers the spec's open question. Integer cents keep sums exact. With no write policy and the time and user derived from `now()` and `auth.uid()`, a payment record can't be back-dated or attributed to someone else, even by an Admin calling PostgREST directly. This is the same reasoning as consent (2026-09-23). Removing a mistake is a hard delete rather than a void flag: for now these are the Admin's own notes of money received, and a void flag can come with Stripe if it's needed. `import_commit()` and `register_kid()` upsert rather than replace the registration, so payments survive a re-import or a parent re-saving the form, and tests cover both. When Stripe arrives it should add its columns here rather than start a parallel table.
- **Reference:** `project_spec.md` §2.4, §2.8; [`decisions.md`](./decisions.md) 2026-10-05; Linear [ENG-9](https://linear.app/cis-app/issue/ENG-9/registration-payment-methods-on-the-parent-form-admin-payment-tracking)

### 2026-09-28 — Parent registration writes go through SECURITY DEFINER functions
- **Status:** Accepted
- **Context:** ENG-4 lets a Parent create a kid and a registration. Until now only an Admin could write either table. The obvious route is to add Parent INSERT/UPDATE policies on `kids` and `registrations`.
- **Decision:** No new write policies. Writes go through `register_kid()`, and imported kids are attached by `link_my_kids()`, both `SECURITY DEFINER` with an explicit `has_role('parent')` check, the same pattern as `import_commit()` and `set_registrations_consent()`. `link_my_kids()` runs when the registration page loads, not at signup. A `seasons` SELECT policy lets a parent read the current season.
- **Consequences / tradeoffs:** A registration is two rows, so one function call means one transaction and no half-registered kid. Consent time and user are derived in the database and cannot be forged by whoever calls PostgREST. An UPDATE policy on `kids` cannot restrict which columns change, so it would let a parent rewrite `parent_user_id`, `skill_tags` and the locked identity fields; the function updates an explicit column list instead. The cost is that the rules live in PL/pgSQL rather than declarative policies, and each error case needs a code the Server Action maps to a message. Linking on page load means it does not depend on the signup flow, at the price of one extra RPC per load; it relies on email confirmation being enabled in production, because with it off Supabase treats every address as confirmed.
- **Reference:** `project_spec.md` §2.4; Linear [ENG-4](https://linear.app/cis-app/issue/ENG-4/kid-registration-parent-self-service-form)

### 2026-09-22 — The kid identity index is deliberately not unique
- **Status:** Accepted
- **Context:** The CSV importer matches returning kids on first name + last name + DOB, case-insensitively and whitespace-trimmed. The old flat table enforced that combination with a UNIQUE index (`registrations_identity_key`).

### 2026-09-22 — Roles modeled as a `user_roles` join table, not a `role[]` array on `User`
- **Status:** Accepted. The `is_staff()` / `is_coach()` helpers it describes were removed on 2026-10-19 (see [Roles are checked only through `has_role()`](#2026-10-19--roles-are-checked-only-through-has_role-signup-creates-roleless-accounts))
- **Context:** `project_spec.md`'s original Core Data Model sketch put `role[]` directly on `User`. The live schema instead only had two booleans (`profiles.is_staff`, `profiles.is_coach`), which cannot express "Admin only, not Program Team" -- a requirement of ENG-5's CSV import (only Admin may run it). A real role model was needed as a foundation before that importer's RLS could be written correctly.
- **Decision:** Added `user_roles` (`user_id`, `role app_role`, `granted_at`, `granted_by`) as a join table, an `app_role` enum (`admin`, `program`, `coach`, `prayer`, `parent`, `kid`), and a `has_role(role)` SQL helper (`SECURITY DEFINER`, mirroring the existing `is_staff()`/`is_coach()` style) -- rather than a `role[]` array column on `profiles`. `is_staff()` is redefined as `has_role('admin')` only and `is_coach()` as `is_staff() OR has_role('coach')`, which is behaviorally identical to every existing RLS policy that calls them, since this migration does not backfill anyone into `'program'` yet -- widening `is_staff()` to include Program Team is left as a deliberate follow-up once that role has real members, not a side effect of this change.
- **Consequences / tradeoffs:** A join table gets its own RLS (who can grant/revoke roles), an audit trail (`granted_at`/`granted_by`), and a real enum + FK, none of which a `text[]`/`role[]` column offers cleanly. It costs one extra join per role check, mitigated by `has_role()` being the single call site. It needed backfilling: from `profiles.is_staff`/`is_coach` (data-driven, not hardcoded ids), plus an explicit admin grant for the project's Director (`joseph.nabil07@gmail.com`), whose `is_staff` flag was false and would otherwise have been locked out of the Admin-only screens this role model gates. RLS is tested against a real local Postgres (`supabase/tests/roles.test.ts`, run via `npm run test:db`, backed by a new CI job that runs `supabase start` -- Docker ships preinstalled on GitHub-hosted runners) rather than mocked, per `AGENTS.md` §7's non-negotiable coverage for role-based access control.
- **Reference:** `project_spec.md` §1.4, §1.5, §2.4 (`User`/`UserRole`); Linear [ENG-5](https://linear.app/cis-app/issue/ENG-5/kid-registration-admin-csv-import)
